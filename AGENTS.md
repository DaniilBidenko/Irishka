# AGENTS.md — инженерные правила «Рабочая тетрадь»

Источник истины для Cursor и разработчиков. Функциональная задача не разрешает переписывать эти правила. Изменение — только по прямому запросу пользователя.

Перед работой: прочитай этот файл и относящиеся разделы `WORKBOOK_MASTER_SPEC.md`. Прогресс многосессионной реализации фиксируй в `IMPLEMENTATION_STATUS.md` без пользовательских данных.

## 1. Scope

Решай только текущую задачу. Перед изменениями коротко перечисли затронутые области и необходимость миграции. Не переименовывай файлы, не форматируй весь проект, не меняй дизайн и зависимости попутно. Не трогай чужие незакоммиченные изменения.

## 2. Разумная самостоятельность

Выполняй необходимые обратимые действия в пределах запроса без постоянных согласований. Прямой запрос пользователя на конкретное изменение правил разрешает его. Если задача требует разрушения данных или расширения функционального scope, сначала объясни конкретный риск и получи явное решение.

## 3. Никаких скрытых работ

Не исправляй найденные посторонние проблемы молча: перечисли их отдельно. Общая зависимость может меняться, если это необходимо задаче; тогда проверь всех её потребителей и объясни влияние.

## 4. Данные

Не работай с реальной БД при разработке/тестах, не отправляй её наружу, не добавляй в Git. Не выводи телефоны, заметки и полный SQL с параметрами в логи. Никаких destructive-команд или обхода защитных проверок ради прохождения теста.

Пользовательские данные: `%LOCALAPPDATA%\WorkNotebook\` (вне репозитория). Dev/test используют временный `DATA_DIR` и собственный `instance_id`. Исчезнувшая БД не заменяется пустой автоматически.

## 5. Миграции

Только новые версионированные миграции; backup и upgrade test обязательны. Нельзя молча переинтерпретировать старое поле, масштаб валюты, timezone или nullable-значение. Переименование UI-подписи не меняет field ID. Выпущенные миграции не редактировать. Production-миграции не применяются при обычном старте — только через controlled update/setup.

## 6. Архитектура

Направление зависимостей: `UI → HTTP adapters → application use cases → domain`. `SQLite / backup / filesystem → application ports`.

Domain чистый (без React, Fastify, SQLite, FS). Use cases содержат бизнес-сценарии. Infrastructure реализует порты. Не обращаться к SQLite из UI/routes и не дублировать корпоративный/розничный код (`client.kind`). Не создавать абстракции на гипотетическое будущее. Нет DI-фреймворка / generic repository / event bus без реальной потребности.

## 7. Сохранение

Каждое поле/настройка имеет запись в `docs/FIELD_PERSISTENCE.md`: UI → DTO → validation → use case → таблица/колонка → тест восстановления после restart. Поле без сохраняемого значения не считается реализованным. SQLite — источник истины; localStorage/IndexedDB — не база (черновики — вспомогательная защита).

## 8. Контракты

Валидация входа на сервере (Zod), параметризованный SQL, revision для конкурирующих записей, idempotency (`operation_id`) для повторов. Не глотать исключения, не показывать ложный успех и не подставлять пустые данные при ошибке чтения БД. Ошибки UI — по-русски без stack trace.

## 9. Код

TypeScript strict, осмысленные имена, небольшие модули, отсутствие `any` без обоснования. Комментарии объясняют причины. Стек: React+Vite, Fastify, better-sqlite3, TanStack Query, Vitest, Playwright.

## 10. Зависимости

Новая библиотека только при реальной пользе; указать причину и стоимость. Не обновлять весь стек ради небольшой задачи, не использовать удалённые runtime-ресурсы (CDN, внешние шрифты). Lockfile обязателен. Не использовать плавающий `latest` в пользовательском установщике.

## 11. UI

Следовать токенам раздела 3 ТЗ и доступности. Не менять смысл кнопок, выбранный месяц или фильтры неожиданно. Статусы загрузки, пустоты, ошибки и сохранения обязательны. Слово «Сохранено» — только после успешного commit и ответа сервера.

## 12. Проверки

Выполнять релевантные тесты; изменение сохранения требует integration test с повторным открытием БД, изменение схемы — upgrade/recovery test. Не удалять и не ослаблять проверки, чтобы скрыть дефект. Не утверждать, что непроведённая проверка прошла.

## 13. Документация

Изменение команд/настроек/путей сопровождается обновлением `START_HERE_RU.md`. Изменение архитектуры — обновлением соответствующего раздела в `docs/` и кратким ADR при новом принципе.

## 14. Git

Не выполнять force push, reset --hard, clean -fd, публикацию или переписывание истории без прямого разрешения. Не коммитить секреты, sqlite, backups, logs. Сам факт реализации не означает разрешение публиковать проект.

## 15. Правила

Не изменять `AGENTS.md`, `.cursor/rules` и `WORKBOOK_MASTER_SPEC.md`, чтобы оправдать несоответствие реализации. На прямую просьбу пользователя менять только нужные пункты, сохраняя остальные. Сначала показать смысл изменения; если ослабляется защита данных — назвать последствия.

## 16. Отчёт

Кратко: что изменено, почему, какие тесты выполнены, что осталось непроверенным. Не выдавать TODO, заглушку, localStorage-прототип или только красивый экран за завершённую функцию.

---

Ключевой принцип: **код можно заменить, пользовательские данные — нельзя.**
