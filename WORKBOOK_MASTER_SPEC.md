# Рабочая тетрадь — единое техническое задание для Cursor

Версия задания: 1.0 · 25 октября 2026. Язык продукта и документации: русский.

> **Инструкция Cursor.** Прочитай файл целиком. Это задание на реализацию полноценного локального приложения, а не на макет. Сначала создай правила из раздела 15, затем реализуй проект по этапам раздела 18. Все перечисленные требования входят в первую версию, кроме явно помеченных «в будущем». Не останавливайся после интерфейса или создания структуры. Не заявляй о готовности до выполнения критериев приёмки. Если работа занимает несколько сессий, сохраняй фактический прогресс в `IMPLEMENTATION_STATUS.md` без пользовательских данных.

## 1. Назначение и исходные решения

Приложение для одного человека, который ведёт клиентов и монтажи на своём компьютере. Три основных раздела: **Корпоративные клиенты**, **Розница**, **Монтажи**. Интернет нужен только для первоначальной установки и получения обновлений. Повседневная работа, поиск, сохранение и резервирование работают без интернета.

Это локальный веб-интерфейс: один фоновый сервер отдаёт собранный интерфейс и API на `http://127.0.0.1:4318`. Нет хостинга, облачной БД, подписок, внешней авторизации и внешних сервисов во время работы. Основная целевая система — Windows 11 x64; это допущение, поскольку ОС не указана. Не утверждать поддержку других ОС без проверки. Бизнес-код и Node-скрипты делать переносимыми; обязательные ярлыки и пользовательские сценарии реализовать для Windows.

Основные определения:

- **Клиент** принадлежит корпоративному или розничному разделу.
- **Монтаж** — одна самостоятельная запись клиента с датами, деньгами, заметками и шестью переключаемыми этапами.
- **Месячный список** — представление монтажей по рабочей дате, не отдельная копия данных.
- **Монтажи** — общее представление этих же записей. Изменение в любом месте меняет одну и ту же сущность.
- **Деление / плашка** в исходной идее означает монтаж. Отдельную сущность группировки в первой версии не вводить.

Сохранность — проверяемые механизмы: транзакции, отдельная папка данных, резервные копии, корзина, контроль конфликтов, безопасные миграции и восстановление. Нельзя обещать абсолютную защиту от поломки диска, удаления пользователем или потери компьютера. Копия на том же диске защищает от части ошибок, но не от потери диска. Предусмотреть копирование резервных архивов на выбранный внешний накопитель.

## 2. Границы первой версии

Реализовать CRUD клиентов и монтажей, закрепление клиентов, месяцы и годы, даты и сроки, этапы, завершение, поиск и фильтры, подробности и предпросмотр, дополнительные поля, изменение размеров и порядка полей, постоянные настройки интерфейса, корзину, локальные черновики, резервирование, восстановление, диагностику, безопасное обновление и документацию.

Не добавлять без отдельного запроса: облачную синхронизацию, роли, CRM-интеграции, бухгалтерию, внешние уведомления, AI-функции, многопользовательскую работу, вложения, загрузку файлов, Electron, Docker, микросервисы, публичную публикацию. CRM и YOU — только подписи ручных этапов, а не интеграции. Не расшифровывать придуманные значения сокращений.

## 3. Визуальное направление: светлая рабочая книга

Спокойный, читаемый, тёплый интерфейс. Основная метафора — аккуратные листы и закладки. Не имитировать бумагу тяжёлыми текстурами. Без стеклянных панелей, кислотных градиентов и лишних иллюстраций.

### 3.1. Токены дизайна

| Назначение | Значение |
|---|---|
| Основной фон | `#F6F3EC` — тёплая бумага |
| Поверхности карточек | `#FFFEFA` |
| Фон выделенного блока | `#EEE8DB` |
| Основной текст | `#292D29` |
| Вторичный текст | `#5F665E` |
| Разделители | `#DCD6C8` |
| Основной акцент | `#486B59` |
| Hover нейтральный | `#F0EDE4` |
| Завершённая карточка | `#E8F0E5` |
| Опасное действие | `#A33D35` |
| Радиус карточки / кнопки | 12 / 8 px |
| Сетка отступов | 4, 8, 12, 16, 24, 32 px |
| Тени | почти незаметные; рамка важнее тени |

Основной шрифт: системный `Segoe UI`, затем system-ui, sans-serif. Текст 16 px, подписи не меньше 13 px, заголовок раздела 22–24 px. Деньги — tabular-nums. Цвета — исходные токены, проверить контраст WCAG AA; при необходимости сделать текст темнее. Размер шрифта доступен в настройках: обычный / крупный. Никаких удалённых шрифтов, CDN и сетевых картинок.

### 3.2. Раскладка экрана клиента

На экране 1440×900:

1. Верхняя полоса высотой 64 px: небольшое название «Рабочая тетрадь», три текстовые вкладки, справа индикатор сохранения и кнопка настроек. Активная вкладка имеет светло-зелёную подложку и подчёркивание.
2. Слева панель клиентов шириной 260 px, вертикальный скролл независимый. Заголовок, поиск, «+ Клиент», список. Кнопка сворачивания оставляет рейку 56 px с понятной кнопкой раскрытия. Не показывать бессмысленные инициалы без подсказок.
3. Справа рабочая область с отступами 24 px. Верхняя выделенная полоса: слева карточка общей информации шириной примерно 320 px; справа год и сетка из 12 месяцев. На 1280 px допускается два ряда по 6 месяцев.
4. Ниже заголовок «Монтажи · Март 2026», число записей, «+ Монтаж», переключатель видимости завершённых.
5. Вертикальный список широких карточек. Карточки занимают всю оставшуюся ширину, промежуток 10–12 px, минимальная высота 112 px, высота растёт при увеличении текста.

Карточка слева направо: **даты 132 px → этапы 126 px → название и краткое описание flex → завершение/меню 64 px**. Между блоками тонкие вертикальные разделители. Длинное название до двух строк, краткое описание до двух строк, полный текст доступен в подробностях. Никакого общего горизонтального скролла страницы.

### 3.3. Адаптивность и доступность

Минимальная обязательная проверка: 1280×720, 1440×900, 1920×1080, браузерный масштаб 125% и 150%. На узком экране панель клиентов выезжает поверх, верхний блок становится вертикальным, карточка переносит блоки в две строки. Подробности занимают экран. Не обещать отдельное мобильное приложение.

Все действия доступны с клавиатуры. Видимый focus-ring, подписи кнопок, `aria-pressed` у этапов, настоящий checkbox завершения. Цвет всегда дублируется словами, значком или состоянием. Tooltip не является единственным объяснением. Esc закрывает незакреплённый предпросмотр; в редакторе учитываются несохранённые изменения. В диалоге — корректное управление фокусом и возврат на исходную карточку.

## 4. Корпоративные клиенты и розница

Оба раздела используют одни компоненты и use cases с параметром `client.kind`; копирование реализации запрещено.

### 4.1. Клиенты

Поля: название организации / отображаемое имя, контактное имя, телефон как строка, заметка. В рознице подпись первого поля «Клиент». Название обязательно, остальные поля необязательны. Телефон допускает `+`, пробелы, скобки, добавочный номер. Не хранить телефон числом. Совпадающие имена допустимы; идентичность определяется ID.

Создание, редактирование, перенос в корзину, восстановление, закрепление, открепление. Несколько клиентов можно закрепить; для них есть устойчивый `pin_order`. По умолчанию при новом открытии раздела выбран первый доступный закреплённый клиент. Если закреплённых нет — последний выбранный доступный, иначе первый в списке. Явная ссылка на конкретный монтаж имеет приоритет над выбором по умолчанию. При переключении разделов в текущей сессии сохранять текущий контекст.

Закреплённые сверху с иконкой булавки, остальные по русскому алфавиту. Можно выбрать «Открывать по умолчанию» для закреплённого: переместить его на первое место, не создавать второй конфликтующий признак. Поиск по названию, контакту, телефону. Состояние панели и её ширина сохраняются.

Удаление клиента с монтажами: диалог с количеством затрагиваемых записей. Одна транзакция помещает клиента и его активные монтажи в корзину. Без физического каскадного удаления. Восстановление группы возвращает только записи, удалённые этой операцией, а не более ранние отдельно удалённые монтажи.

### 4.2. Общая информация и месяцы

Карточка информации вверху: название, контакт, телефон, кнопка «Изменить». Редактирование в явной форме с «Сохранить» / «Отмена»; индикатор статуса обязателен.

Справа: переключатель года, «Сегодня», месяцы Янв–Дек с количеством активных монтажей. Доступны прошедшие и будущие годы, без искусственной привязки к году установки. Год можно вводить и переключать стрелками. Текущий месяц — тонкая рамка, выбранный — зелёная подложка. Выбор года сохраняет месяц, «Сегодня» выбирает текущие год и месяц.

При первом открытии — текущий месяц локального календаря компьютера. Далее последний выбранный период сохраняется для каждого клиента. Монтаж попадает в месяц по `work_date`, **не по сроку сдачи**. Перенос `work_date` в другой месяц перемещает запись между представлениями; показать уведомление с кнопкой перехода.

Новый монтаж получает рабочую дату сегодня, если открыт текущий месяц; иначе первое число выбранного месяца. Дату показать до сохранения. Пустой месяц: «В этом месяце пока нет монтажей» и кнопка добавления. Пустой список клиентов: краткое объяснение и «Добавить первого клиента».

## 5. Монтаж и его карточка

### 5.1. Поля

| Поле | Тип / правило |
|---|---|
| ID | UUID, неизменяемый |
| Клиент | обязательный FK |
| Название | 1–200 символов после trim |
| Краткая информация | до 1000 символов |
| Рабочая дата | обязательная календарная дата `YYYY-MM-DD` |
| Срок сдачи | необязательная календарная дата |
| Цена | необязательное целое число в минимальных единицах валюты |
| Себестоимость | аналогично |
| Монтаж | денежная стоимость монтажных работ; допущение первой версии |
| Заметки | многострочный обычный текст, до 100000 символов |
| Выполнено | boolean и `completed_at` |
| Этапы | CRM, YOU, ПП, МОН, ГВ, СО — шесть независимых boolean |
| Служебные данные | created_at, updated_at, revision, deleted_at, deletion_batch_id |

«Монтаж» как денежное поле — выбранное толкование неоднозначного слова в исходном запросе. Подпись в форме «Монтаж, стоимость работ». Произвольное текстовое описание работ помещается в заметках/дополнительном поле. Формулы прибыли не вводить: неизвестно, включены ли монтажные работы в себестоимость. Валюта выбирается при первом запуске из справочника либо вводится код; не угадывать её по языку. У записи хранить код валюты и используемый масштаб. Смена валюты по умолчанию не переобозначает старые суммы и не конвертирует их.

Пустая денежная сумма отличается от нуля. Decimal ввод разбирать точно, не через двоичную арифметику float. Принимать запятую или точку; запрещать больше допустимого числа десятичных знаков и выход за безопасный диапазон integer. Отрицательные суммы в первой версии не допускаются. Деньги разных валют не суммировать.

### 5.2. Цвет срока

Сравнивать календарные дни в локальном часовом поясе приложения; хранить даты без UTC-преобразований, timestamps — UTC. Порог «скоро» настраиваемый, начальное значение 3 дня. Начальные состояния:

| Условие для незавершённого | Вид |
|---|---|
| Нет срока | серый, «Без срока» |
| Больше 3 дней | зелёный, «Осталось N дн.» |
| 2–3 дня | янтарный, «Скоро · N дн.» |
| 1 день | красный, «Завтра» |
| 0 дней | красный, «Сегодня» |
| Меньше 0 | тёмно-красный, «Просрочено на N дн.» |
| Завершён | нейтрально-зелёный, «Выполнено»; срок остаётся видимым |

Срок раньше рабочей даты допускается только после понятного предупреждения, чтобы не препятствовать вводу истории. Пересчёт при старте, в локальную полночь и при возвращении фокуса. Историческую своевременность определять по дате завершения, если она показывается; не считать завершённую карточку просроченной только потому, что сегодня позднее срока.

### 5.3. Этапы 2×3

Порядок строго: верхняя строка **CRM · YOU · ПП**, нижняя **МОН · ГВ · СО**. Кнопки примерно 36×32 px с промежутками 4 px, с областью нажатия не меньше 36 px. Выключенные — приглушённый нейтральный фон с читаемой подписью. Включённые полностью залиты своим цветом: CRM синий `#315D82`, YOU фиолетовый `#675184`, ПП охра `#7B5C20`, МОН бирюзовый `#236B66`, ГВ зелёный `#436A35`, СО ягодный `#8D455D`. Проверить контраст белых подписей.

Клик устанавливает требуемое состояние, повторный снимает. Этапы независимы и не обязаны идти по порядку. Переключение не открывает подробности. Пока операция выполняется, защищать конкретную кнопку от повторной гонки. API принимает `enabled: true/false`, а не команду toggle, чтобы повтор сетевого запроса не инвертировал значение второй раз.

### 5.4. Завершение

Отдельная галочка «Монтаж выполнен». Не требовать шести включённых этапов и не включать их автоматически. После успешного сохранения фон становится мягко-зелёным, появляется «Выполнено», визуальный акцент приглушается без ухудшения контраста текста. Однократное лёгкое конфетти 600–900 ms, без звука и блокировки управления. Не запускать эффект при загрузке, синхронизации вкладок или повторе запроса. Учитывать reduced-motion и переключатель анимаций.

Снятие галочки возвращает активное состояние, обнуляет текущее completed_at, сохраняя историю действия. В общем разделе и карточке клиента состояние одинаково. При ошибке записи вернуть прежнее отображение и показать ошибку.

## 6. Предпросмотр и подробности

Правая текстовая область карточки — основная зона открытия. Hover после 450 ms показывает **временный предпросмотр только для чтения**; уход с карточки и панели закрывает его с задержкой 200 ms, чтобы можно было перевести курсор. Это popover, не модальный диалог и не редактор. Клавиатурный эквивалент — кнопка «Предпросмотр». Touch — только явное открытие.

Клик по названию закрепляет **панель подробностей справа**, ширина 50vw, минимум 560 px при достаточном экране, максимум 840 px. На узком экране — 100%. Подложка слегка затемнена; слева остаётся контекст. Заголовок, клиент и период, статус сохранения, закрытие. Поля названия, описания, дат, денег, заметок, этапов и завершения доступны внутри панели. Внизу «Сохранить сейчас». Кнопка «Открыть у клиента» особенно заметна из общего списка.

### 6.1. Размеры и расположение полей

Реализовать сетку из 12 колонок. В режиме «Настроить поля» поле можно переместить за отдельный drag handle и менять размер: ширина 3/6/12 колонок, высота в диапазоне, подходящем типу. Для однострочных полей растягивается контейнер, для заметок — область текста. Предоставить кнопки перемещения и выбора размера как клавиатурную альтернативу drag-and-drop.

Хранить `field_key`, `order`, `column_span`, `height` и `layout_version` в SQLite. Один основной макет на пользователя и отдельная компактная раскладка; не переносить пиксельную ширину большого монитора на маленький. «Сбросить расположение» сбрасывает только макет, не данные. Новые поля вставляются в конец и не сбрасывают существующие настройки. Идентификаторы полей не зависят от подписи.

### 6.2. Дополнительные поля

В настройках редактора можно добавить собственное поле: текст, многострочный текст, число или дата. Определение общее для монтажей, значение отдельное у каждой записи. Имя обязательно; внутренний ID постоянный. Переименование не теряет значений. Удаление определения означает архивирование, значения сохраняются и доступны после восстановления. Тип поля с уже существующими значениями нельзя менять без отдельной проверяемой миграции. Системные поля удалять нельзя.

## 7. Общий раздел «Монтажи»

Единый список корпоративных и розничных записей; карточка использует тот же UI-компонент и те же API-команды. Дополнительная строка карточки: тип клиента и его название. Подробности открываются кликом по названию монтажа; ссылка «К клиенту» ведёт сразу к нужному клиенту, году и месяцу, прокручивает к записи и кратко подсвечивает её.

Фильтры: строка поиска по названию/краткому описанию/названию клиента; тип клиента; конкретный клиент; диапазон рабочей даты; диапазон срока; активные/выполненные/все; без срока/скоро/просроченные; состояния отдельных этапов. Несколько условий сочетаются через AND, выбранные значения одного фильтра — через OR. Для этапа три значения: любой / включён / выключен. Показать активные фильтры и «Сбросить». По умолчанию — активные, все клиенты, без ограничения месяца.

Поиск регистронезависимый для кириллицы. Для первой версии нормализовать поисковую строку в приложении (Unicode NFKC, lower-case, ё→е, пробелы) и хранить поисковые значения; не полагаться на SQLite NOCASE для русского языка. Параметризовать запросы, экранировать `%` и `_` для literal-поиска. Debounce 250 ms, отмена устаревшего запроса.

Сортировка: срок сдачи (без срока в конце), рабочая дата, название, дата изменения; стабильный второй ключ ID. По умолчанию — срок по возрастанию, затем рабочая дата. Пагинация 50 записей, без загрузки всей базы. Показывать количество найденных и состояние «Ничего не найдено».

Маршруты: `/corporate/:clientId?year=2026&month=3&installation=:id`, `/retail/:clientId?...`, `/installations?...filters`. URL содержит только навигационные параметры и ID, не контактные данные. Fallback сервера возвращает SPA для прямой ссылки. Удалённая запись вызывает понятное сообщение и переход в корзину, не пустой экран.

## 8. Сохранение и конфликты

SQLite — источник истины. React state — состояние формы и кэш, localStorage не является базой. Все пользовательские поля, дополнительные значения, макеты, фильтры и настройки, которые должны пережить перезапуск, имеют явное место в SQLite.

Текстовый редактор: автосохранение после 600 ms без ввода и при blur; «Сохранить сейчас» выполняет немедленно. Показать «Есть изменения», «Сохраняю…», «Сохранено в 14:32», «Не сохранено — повторить». Слово «Сохранено» допустимо только после успешного commit и ответа сервера. Создание записи — явная кнопка, до неё данные являются черновиком. Галочки и даты сохранять сразу после подтверждённого ввода.

Для несохранённого ввода — аварийный черновик в IndexedDB с `entity_id`, `base_revision`, timestamp и изменёнными полями; очищать только после подтверждённой записи соответствующей версии. Это вспомогательная защита, не основное хранилище. При недоступности браузерного хранилища показывать предупреждение. При повторном открытии предложить восстановить черновик с сравнением версии; никогда молча не затирать более новые серверные данные. Невалидный ввод остаётся в форме/черновике и не портит сохранённое значение.

При переключении записи/закрытии редактора дождаться записи; при ошибке дать «Остаться», «Повторить», «Закрыть с сохранённым черновиком». На закрытие вкладки использовать beforeunload при наличии pending; не обещать надёжный сетевой flush при закрытии браузера или отключении питания.

Каждая изменяемая сущность имеет revision. PATCH передаёт ожидаемую revision; SQL обновляет только при совпадении и увеличивает её. При конфликте вернуть 409, показать серверные и локальные изменения и предложить решение. Отдельная очередь записи на сущность предотвращает гонки автосохранения и кнопок. Не отправлять всю устаревшую карточку при изменении одной галочки.

Создание и повторяемые команды поддерживают operation_id для идемпотентности. Смена этапов, custom values и записи истории происходит в одной транзакции с увеличением общей revision монтажа. После мутации обновляются все соответствующие кэши. Несколько вкладок: BroadcastChannel сообщает об изменениях, другие вкладки перечитывают данные; при focus также revalidate. Открытый изменённый черновик не заменяется без предупреждения.

## 9. Стек и луковая архитектура

Выбранный стек: TypeScript strict; React + Vite; локальный Node.js сервер Fastify; SQLite через better-sqlite3; SQL-миграции под собственным небольшим контролируемым runner; Zod на границах; TanStack Query для server-state; Vitest для unit/integration; Playwright для E2E. UI — CSS variables/CSS Modules и небольшой набор доступных компонентов. Не добавлять большой UI-фреймворк без необходимости.

Использовать поддерживаемую LTS-ветку Node 24, точный patch и совместимые версии зависимостей проверить при реализации, зафиксировать в проекте и lockfile. Отдельно проверить установку native-модуля SQLite на Windows x64 без ручной установки компилятора; несовместимость обнаружить до передачи тёте. Не использовать плавающий `latest` в пользовательском установщике. Обновления зависимостей — отдельная задача.

### 9.1. Направление зависимостей

`UI → HTTP adapters → application use cases → domain`

`SQLite / backup / filesystem adapters → application ports`

Domain ничего не знает о React, Fastify, SQLite, файловой системе. Application зависит от domain и интерфейсов портов; infrastructure реализует порты. Composition root связывает реализации. HTTP — адаптер, бизнес-решения не живут в route handlers. UI не имеет доступа к БД и не импортирует infrastructure. Зависимости контролировать lint-правилами/проверкой импортов в CI.

### 9.2. Структура репозитория

Не создавать интерфейс ради каждого класса; порты нужны на границах: репозитории, транзакции, время, ID, backup, настройки. Не вводить DI-фреймворк, generic repository или event bus без реальной потребности.

Use cases: Create/Update/Trash/RestoreClient, PinClient; Create/Update/Trash/RestoreInstallation, SetStage, SetCompleted; QueryInstallations, GetClientMonth; SaveLayout, Define/ArchiveCustomField; Create/Verify/RestoreBackup. Правила дат и валют — чистые функции с внедряемыми часами. Запросы списков могут использовать отдельный query port с DTO без реконструкции всех агрегатов.

## 10. Модель SQLite

Минимальные таблицы:

| Таблица | Содержание |
|---|---|
| clients | id, kind CHECK corporate/retail, display_name, contact_name, phone, notes, pin_order nullable, revision, timestamps, deleted_at, deletion_batch_id |
| installations | id, client_id FK, title, summary, notes, work_date, due_date nullable, price_minor/cost_minor/installation_minor nullable, currency_code, currency_scale, completed, completed_at, revision, timestamps, deleted_at, deletion_batch_id, normalized_search |
| installation_stages | installation_id FK, stage_code CHECK фиксированных шести кодов, enabled CHECK 0/1; составной PK |
| custom_field_definitions | id, label, type, sort_order, archived_at, revision, timestamps |
| installation_custom_values | installation_id, field_id, typed value columns; составной PK и CHECK согласованности |
| ui_preferences | key PK, version, value_json с проверкой схемы приложением |
| field_layouts | layout_scope, field_key, order, column_span, height, layout_version |
| change_log | id, entity_type/id, operation, changed_fields_json, before/after для изменённых полей, timestamp, operation_id |
| processed_operations | operation_id UNIQUE, результат/идентификатор, timestamp |
| schema_migrations | version PK, checksum, applied_at, app_version |
| app_metadata | постоянный instance_id, created_at, schema compatibility metadata |

Каждый монтаж имеет ровно шесть строк stages, создаваемых одной транзакцией. FK enforcement включён на каждом соединении. Никакого ON DELETE CASCADE для пользовательских сущностей. CHECK constraints для boolean, перечислений и допустимых денежных значений. Ограничения длины и даты проверяются также на сервере. Не хранить всю тетрадь одним JSON-документом. JSON допустим для версионированных UI-настроек и журнала, но не вместо реляционных связей.

Индексы: installations(client_id, work_date, id), installations(completed, due_date, id), installations(updated_at, id), FK поля, clients(kind, deleted_at), active/deleted при необходимости по EXPLAIN QUERY PLAN. Запрос месяца — полуоткрытый диапазон `[первое число; первое число следующего месяца)`, без функций над индексированной датой. Нормализованный поиск обновлять транзакционно при изменении названия/описания; поиск клиента связывать корректно без устаревающей денормализации.

Подключение: `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, разумный `busy_timeout` (начально 5000 ms). Возврат успеха только после commit. Один серверный writer; долгие backup/обслуживание не блокируют UI без статуса. При ошибке блокировки ограниченный retry, затем понятная ошибка, не бесконечный цикл.

Корзина не очищается автоматически. В первой версии постоянное удаление записей через UI не реализовывать. Журнал изменений хранится локально, не уходит в Git и не выдаётся за независимую резервную копию. Просмотр истории записи — в подробностях; восстановление отдельных старых значений можно отложить, восстановление из корзины и резервного архива обязательно.

## 11. Папки данных и защита от случайного обнуления

Код репозитория и реальные данные физически разделены.

На Windows:

- Код исходников: выбранная пользователем папка, например `%USERPROFILE%\WorkNotebook-source`.
- Стабильный launcher/config: `%LOCALAPPDATA%\WorkNotebook\launcher` и `config`.
- Активные собранные версии: `%LOCALAPPDATA%\WorkNotebook\releases\<commit>`.
- БД: `%LOCALAPPDATA%\WorkNotebook\data\workbook.sqlite3`.
- Копии: `%LOCALAPPDATA%\WorkNotebook\backups`.
- Логи: `%LOCALAPPDATA%\WorkNotebook\logs`.

Пути определять независимо от cwd. Config хранит canonical data path и instance_id. Путь не меняется от имени репозитория или версии. Разрешить явный перенос через отдельную обслуживающую команду с backup и проверкой; не пытаться угадывать новую папку.

Если конфигурация уже существовала, но БД пропала, не создавать пустую автоматически. Показать ошибку с прежним путём и действиями «Найти базу», «Восстановить копию». Даже при потере config создание новой базы требует явно подтверждённого первого запуска; поиск данных ограничить известными папками приложения и выбором пользователя. Новая пустая база — только осознанная первичная инициализация, с записью instance_id.

Рабочая БД должна лежать на локальном диске, не в Git, сетевой папке или синхронизируемой папке OneDrive/Dropbox. На внешний накопитель экспортируются завершённые резервные архивы, не работающий файл БД.

`.gitignore`: любые sqlite/db, WAL/SHM, backups, logs, .env с приватными значениями, пользовательские экспорты, runtime и локальные конфиги. Дополнительно CI-проверка tracked files, чтобы база не попала в коммит вопреки ignore. Исключения только для явно синтетических fixtures; предпочтительно создавать их тестовым кодом.

Никаких production seeds при запуске и обновлении. Демо-данные только по отдельной команде с отдельным временным DATA_DIR и большой надписью «Демо». Тесты отказываются работать с реальным DATA_DIR, используют tmp directory и собственный instance_id.

## 12. Backup, миграции и восстановление

### 12.1. Резервные копии

Использовать SQLite Online Backup API, предоставленный выбранным драйвером; нельзя копировать только открытый `.sqlite3` обычным filesystem copy, игнорируя WAL. Архив содержит согласованный snapshot БД, переносимые настройки, manifest: версия приложения, schema_version, instance_id, created_at, размер, SHA-256. Машинные абсолютные пути не переносить слепо на другой компьютер.

Сначала временный файл в том же filesystem, затем проверка `integrity_check` и `foreign_key_check` на snapshot, checksum, закрытие и атомарная публикация готового архива. Неполные архивы не показывать как пригодные. Файловый flush выполнять там, где поддерживается; не обещать аппаратную гарантию.

Автоматически: при первом запуске дня до редактирования; каждые 30 минут при наличии подтверждённых изменений; обязательно перед миграцией, обновлением и восстановлением. Интервальные копии: последние 48; дневные: 30; месячные: 12. Предобновительные и ручные не удалять автоматически. Удаление старых автоматических копий только после успешной проверки новой; последнюю исправную не удалять. При нехватке места не удалять единственную копию ради попытки обновления.

Настройки показывают дату последней успешной копии, кнопку «Создать копию», «Сохранить копию в другую папку», «Открыть папку». Если внешняя папка недоступна, внутреннее копирование продолжает работать, внешнее показывает явную ошибку. Для обновления ошибка обязательного backup блокирует обновление. При обычной работе ошибка очередного backup показывает постоянное предупреждение, не выдает сохранения за резервирование.

### 12.2. Миграции

Миграции версионированы, append-only, с checksum. Уже выпущенную миграцию не редактировать — добавить новую. Проверять диапазон совместимости кода и схемы; старое приложение не должно открывать более новую неподдерживаемую схему на запись.

Автоматическое применение production-миграций при обычном старте запрещено. Первый setup создаёт схему явно. Обновление запускает отдельную контролируемую процедуру: exclusive maintenance lock, проверка backup, пробный прогон на копии, затем транзакционное применение к реальной базе. Запретить schema sync, reset, drop-and-recreate и dev-команды миграций на production.

Предпочитать расширяющие изменения: новые nullable-колонки, таблицы, backfill с явными правилами. Сложный rebuild SQLite-таблицы допустим только как проверенная миграция с сохранением строк, FK, индексов и значений. Проверять контрольные количества и прикладные инварианты, не только успешный SQL. Ошибка любой миграции откатывает её транзакцию; не продолжать частично. Операции вроде VACUUM, которые требуют отдельного режима, не смешивать с атомарным набором миграций.

### 12.3. Восстановление

Только явное действие. Показать дату архива, версию и предупреждение: состояние после даты копии не входит в неё. Сначала создать проверенную копию текущей БД; если текущая повреждена — сохранить её байты как recovery evidence и не уничтожать. Остановить сервер/соединения, проверить архив и допустимость схемы во временной папке, не открывать исходный архив на запись. Подготовить согласованную замену БД; старые WAL/SHM не должны попасть к восстановленному файлу. Держать исходную БД отдельно до успешного health-check. Перезапуск и проверка instance_id, количества клиентов/монтажей, custom values и макетов. При сбое вернуть прежние файлы, ничего не удалять.

Проверить путь восстановления, а не только создание архива. Не реализовывать автоматическую «починку» повреждённой базы путём её удаления.

## 13. Безопасные обновления из репозитория

Просто `git pull && npm install` в работающей папке не является безопасной системой обновления. Репозиторий доставляет код; личные данные не синхронизируются Git.

Реализовать `npm run app:update` и ярлык «Обновить тетрадь». Канал по умолчанию — опубликованные владельцем версионные теги `vX.Y.Z`, содержащие release manifest; не произвольная вершина main. До первого тега setup разрешает явно выбранный проверенный commit с предупреждением разработчику. Remote берётся из конфигурации установки, не переключается автоматически.

Протокол обновления:

1. Проверить Git/Node, сеть, свободное место, чистоту исходного checkout. При локальных изменениях остановиться и объяснить; не делать reset --hard, clean -fd или auto-stash.
2. Fetch и выбор целевого релиза; показать текущую и новую версии. Получить исходники в отдельный staging/worktree без изменения работающей версии. Сборка и `npm ci` происходят там, не затрагивая её node_modules. Зависимости берутся из lockfile.
3. Проверить release manifest, требуемую версию runtime и checksum миграций. Выполнить сборку и проверки на тестовых данных. Нужный новый Node не устанавливать молча поверх системного.
4. Если есть pending-редактирование, попросить закончить сохранение; перевести API в maintenance mode, запретить новые мутации, завершить текущие транзакции. Закрытие браузера не является доказательством завершения записи. Получить единый lock для update/restore/backup maintenance.
5. Создать и проверить предобновительный backup. На копии выполнить миграции и smoke/invariant checks. Ошибка оставляет рабочую версию и исходную БД без изменений.
6. Корректно остановить старый процесс. Применить проверенный набор миграций к основной базе транзакционно. Пока идёт обновление, пользовательская запись запрещена.
7. Атомарно переключить стабильный указатель active-release на готовый каталог. Запустить новую версию. Health-check проверяет версию приложения, схему, instance_id и чтение БД; smoke-check не добавляет тестовые записи в реальную базу.
8. Только после успеха снять maintenance, обновить вкладку и показать «Обновление завершено; данные проверены». Хранить минимум предыдущую рабочую версию.
9. При сбое до открытия записей: вернуть старый код; если схема менялась несовместимо, восстановить предобновительный snapshot под lock. Зафиксировать причину и путь backup. После допуска пользовательских записей откат к старому snapshot **не выполнять автоматически**: он потерял бы новые изменения. Тогда нужен forward-fix или явное восстановление с предупреждением.

Каждый шаг фиксируется в durable update journal вне репозитория. После отключения питания launcher распознаёт незавершённое обновление и входит в режим восстановления, а не начинает новую пустую установку. Проверить остановку после каждого критического шага. Журнал хранит old/new release, snapshot, schema versions и фазу без персональных данных. Управление заменой файлов и остановкой процессов проверить на Windows, где открытые файлы нельзя считать свободно заменяемыми.

Стабильный launcher не находится внутри изменяемого release. Ярлыки указывают на него. Обновление launcher — отдельная контролируемая операция, не самоперезапись выполняющегося скрипта. Повседневный старт не выполняет fetch/install/update и работает без сети.

Владелец устанавливает поддерживаемые Node.js LTS и Git for Windows, создаёт репозиторий и подставляет его действительный URL. Для приватного репозитория один раз настраивает доступ через Git Credential Manager/SSH; токен нельзя хранить в README. Команды PowerShell:

Setup проверяет окружение до создания данных и предлагает выбрать валюту и расположение внешних копий. Права администратора для работы приложения не нужны.

### 14.3. Ежедневная работа

«Нажмите ярлык “Рабочая тетрадь”. Браузер откроется сам. Ссылку `http://127.0.0.1:4318` можно закрепить в закладках. Закладка работает, пока запущена тетрадь; после перезагрузки компьютера сначала используйте ярлык. Интернет не нужен. Дождитесь надписи “Сохранено” перед выключением компьютера».

Повторный запуск проверяет identity endpoint уже работающего приложения и открывает его, не создавая второй writer. Если порт занят чужой программой — понятная ошибка, не убивать чужой процесс и не менять порт молча. Порт можно изменить явно с обновлением ярлыков/документации. Проверять pid и instance identity, не доверять одному pid-файлу. Запуск скрытый/фоновый, логи ротируются. Закрытие вкладки не останавливает сервер. «Остановить тетрадь» корректно завершает процесс. Автозапуск при входе в Windows — отдельная опция, выключенная по умолчанию.

Типовые проблемы в README: сервер не запущен, порт занят, недостаточно места, нет интернета для update, версия Node не подходит, БД не найдена, запись не сохранилась. Для каждой — конкретное безопасное действие. «Удалить базу и запустить заново» никогда не является решением.

## 15. Обязательные правила Cursor

Сначала создать `AGENTS.md` как главный редактируемый документ инженерных правил и `.cursor/rules/00-project.mdc` как автоматически применяемую инструкцию. Пользователь может просить изменять эти файлы через Cursor, но обычная функциональная задача не является разрешением переписать правила.

Содержимое `.cursor/rules/00-project.mdc`:

```mdc
---
description: Обязательные правила локальной рабочей тетради, области изменений и сохранности данных
alwaysApply: true
---
Перед изменениями прочитай AGENTS.md и относящиеся к задаче разделы WORKBOOK_MASTER_SPEC.md.
Изменяй только необходимое для текущего запроса. Не делай попутный рефакторинг.
Пользовательские данные находятся вне репозитория. Не удаляй и не пересоздавай их.
Не запускай reset/schema sync/production seeds и не редактируй выпущенные миграции.
Соблюдай направление зависимостей domain <- application <- adapters.
Каждое редактируемое поле должно иметь постоянное хранение и проверку сохранения.
Правила меняются только по прямому запросу пользователя; противоречия не устраняй молча.
В завершении сообщи изменения, выполненные проверки и непроверенные ограничения.
```

Содержимое `AGENTS.md` должно включать следующие обязательные правила:

1. **Scope.** Решай только текущую задачу. Перед изменениями коротко перечисли затронутые области и необходимость миграции. Не переименовывай файлы, не форматируй весь проект, не меняй дизайн и зависимости попутно. Не трогай чужие незакоммиченные изменения.
2. **Разумная самостоятельность.** Выполняй необходимые обратимые действия в пределах запроса без постоянных согласований. Прямой запрос пользователя на конкретное изменение правил разрешает его. Если задача требует разрушения данных или расширения функционального scope, сначала объясни конкретный риск и получи явное решение.
3. **Никаких скрытых работ.** Не исправляй найденные посторонние проблемы молча: перечисли их отдельно. Общая зависимость может меняться, если это необходимо задаче; тогда проверь всех её потребителей и объясни влияние.
4. **Данные.** Не работай с реальной БД при разработке/тестах, не отправляй её наружу, не добавляй в Git. Не выводи телефоны, заметки и полный SQL с параметрами в логи. Никаких destructive-команд или обхода защитных проверок ради прохождения теста.
5. **Миграции.** Только новые версионированные миграции; backup и upgrade test обязательны. Нельзя молча переинтерпретировать старое поле, масштаб валюты, timezone или nullable-значение. Переименование UI-подписи не меняет field ID.
6. **Архитектура.** Domain чистый, use cases содержат бизнес-сценарии, infrastructure реализует порты. Не обращаться к SQLite из UI/routes и не дублировать корпоративный/розничный код. Не создавать абстракции на гипотетическое будущее.
7. **Сохранение.** Каждое поле/настройка имеет запись в FIELD_PERSISTENCE.md: UI → DTO → validation → use case → таблица/колонка → тест восстановления после restart. Поле без сохраняемого значения не считается реализованным.
8. **Контракты.** Валидация входа на сервере, параметризованный SQL, revision для конкурирующих записей, idempotency для повторов. Не глотать исключения, не показывать ложный успех и не подставлять пустые данные при ошибке чтения БД.
9. **Код.** TypeScript strict, осмысленные имена, небольшие модули, отсутствие any без обоснования. Комментарии объясняют причины. Ошибки отображаются по-русски без stack trace в UI.
10. **Зависимости.** Новая библиотека только при реальной пользе; указать причину и стоимость. Не обновлять весь стек ради небольшой задачи, не использовать удалённые runtime-ресурсы. Lockfile обязателен.
11. **UI.** Следовать токенам и доступности. Не менять смысл кнопок, выбранный месяц или фильтры неожиданно. Статусы загрузки, пустоты, ошибки и сохранения обязательны.
12. **Проверки.** Выполнять релевантные тесты; изменение сохранения требует integration test с повторным открытием БД, изменение схемы — upgrade/recovery test. Не удалять и не ослаблять проверки, чтобы скрыть дефект. Не утверждать, что непроведённая проверка прошла.
13. **Документация.** Изменение команд/настроек/путей сопровождается обновлением START_HERE_RU.md. Изменение архитектуры — обновлением соответствующего раздела и кратким ADR, если это действительно новый принцип.
14. **Git.** Не выполнять force push, reset --hard, clean -fd, публикацию или переписывание истории без прямого разрешения. Не коммитить секреты. Сам факт реализации не означает разрешение публиковать проект.
15. **Правила.** Не изменять AGENTS.md, .cursor/rules и это ТЗ, чтобы оправдать несоответствие реализации. На прямую просьбу пользователя менять только нужные пункты, сохраняя остальные. Сначала показать смысл изменения; если ослабляется защита данных — назвать последствия.
16. **Отчёт.** Кратко: что изменено, почему, какие тесты выполнены, что осталось непроверенным. Не выдавать TODO, заглушку, localStorage-прототип или только красивый экран за завершённую функцию.

Не создавать второй расходящийся список правил в устаревшем `.cursorrules`. Дополнительные scoped .mdc допустимы для data-safety и frontend, но должны ссылаться на основной источник, а не противоречить ему. Правила ИИ помогают дисциплине, но не заменяют тесты, ограничения БД и review.

## 16. Локальная безопасность и API

Сервер слушает **только 127.0.0.1**, не 0.0.0.0. UI и API одного origin. Проверка Host, запрет произвольного CORS и проверка Origin для мутаций защищают от обращения чужих сайтов к localhost; одна проверка CORS недостаточна. Использовать локальную сессию и CSRF token, SameSite cookie, серверную проверку Content-Type. Токены не помещать в URL или Git. Подробную модель локальной защиты проверить интеграционными тестами, включая отсутствие Origin у недоверенного запроса.

CSP без сторонних источников, пользовательский текст рендерить как текст, не HTML. Ограничить размеры request body и строк. Файловые операции доступны только через узкие команды backup/restore с проверкой путей, не универсальный HTTP-доступ к файловой системе. Нет телеметрии и отправки логов автоматически. Это не шифрование диска: пользователь с доступом к OS-профилю может прочитать данные; при необходимости используется защита самого компьютера.

API `/api/v1`: ресурсы clients, installations, custom-fields, preferences, trash, backups; отдельные действия stages/completion. GET не меняет бизнес-данные. PATCH — только разрешённые поля. Ошибки `{code, message, details?, requestId}`; 400 validation, 404 missing, 409 revision/maintenance conflict, 503 unavailable. Сервер возвращает обновлённую сущность/revision после записи. Health endpoint не раскрывает контакты и заметки.

## 17. Производительность и качество

Целевой профиль: обычный Windows-ноутбук, SSD, 8 GB RAM, до 2000 клиентов и 50000 монтажей. Это ориентиры для измерения, не уже доказанные результаты. Первое открытие локального UI — до 2 секунд после готовности сервера, страницы списка и поиск p95 до 300 ms на таком наборе при прогретой БД. Указать реальную тестовую машину и результаты, не подгонять цифры.

Не держать все карточки в DOM, пагинация 50; виртуализацию добавлять при подтверждённой необходимости. Избегать N+1 запросов; этапы читать пакетно. Кэшировать только с корректной инвалидизацией. Локальная сборка ассетов, code splitting редактора при пользе. Долгие операции имеют прогресс и не подвешивают серверный event loop; backup выполнять поддерживаемым асинхронным механизмом/worker. Никаких преждевременных сложных кешей поверх SQLite.

Матрица проверок:

| Проверка | Что доказывает |
|---|---|
| Unit: дедлайны | границы 4/3/2/1/0/−1 дней, leap year, смена месяца, завершение, DST |
| Unit: деньги | пусто/0, запятая, масштаб, слишком большое значение, отсутствие float-ошибок |
| Integration: persistence | все поля, custom values, этапы, pin и layout переживают close/open БД |
| Integration: atomicity | ошибка в середине операции не сохраняет половину изменений |
| Integration: conflicts | две revision не теряют значения; retry create не создаёт дубль |
| Integration: trash | удаление/восстановление клиента и отдельных монтажей с deletion_batch |
| E2E: связи | изменения в клиенте видны в «Монтажи» и обратно, переход открывает правильный месяц |
| E2E: editor | hover не редактирует, click закрепляет, размеры/порядок переживают перезапуск |
| E2E: error | сбой API/диск заполнен не показывает «Сохранено», черновик восстанавливается |
| E2E: offline | после установки работа без доступа к интернету, нет внешних запросов |
| Backup/restore | открытие восстановленного архива, сравнение всех данных и настроек |
| Upgrade | старая схема с разнообразными данными → новая; сохраняются значения и ID |
| Failure injection | обрыв после backup, migration, switch-release, health-check; безопасный restart |
| Runtime | второй запуск, чужой занятый порт, пробелы/кириллица в пути, потерянная БД |
| Security | Host/Origin/CSRF, SQL-injection входы, HTML как текст, path traversal |

Для upgrade fixtures создавать синтетическую базу каждой поддерживаемой предыдущей схемы. Проверять сохранение Unicode, пустых и нулевых значений, archived custom fields, корзины и layout; сравнивать данные по ID и семантике, а не по бинарному совпадению SQLite-файлов. Симулировать ошибки диска/процесса только в изолированной временной среде.

## 20. Источники технических решений

Официальные справочные материалы проверены при подготовке задания. Они поясняют механизмы; выбранные продуктовые требования, пороги и архитектура заданы настоящим ТЗ.

- Cursor Project Rules / `.cursor/rules`: https://cursor.com/docs/rules
- SQLite Online Backup API: https://www.sqlite.org/backup.html
- SQLite PRAGMA, в том числе synchronous и foreign_keys: https://www.sqlite.org/pragma.html
- SQLite WAL: https://www.sqlite.org/wal.html
- Поддерживаемые ветки Node.js: https://nodejs.org/en/about/previous-releases

**Ключевой принцип при любых будущих доработках:** код можно заменить, пользовательские данные — нельзя. Новая функция готова только тогда, когда сохраняет старые данные, имеет определённое постоянное хранение новых значений и проверена вместе с затронутыми сценариями.
